# H2O.ai db-benchmark — lazy pandas vs Polars

Faithful port of the [DuckDB Labs db-benchmark](https://github.com/duckdblabs/db-benchmark)
(group-by + join) against our lazy API and Polars. Generated by
`bench_h2o.py`; see `../docs/BENCHMARK_SUITES.md` for methodology.

- **Scale:** 10,000,000 rows (1e7, ~0.5 GB), key cardinality k=100.
- **Hardware:** 8-core Apple Silicon laptop.
- **Convention:** each query run twice (cold, hot), per the benchmark. Joins
  collect with `order="relaxed"` (H2O does not constrain output order — the
  fair comparison vs Polars, which is also unordered).
- **`hotx`** = Polars_hot / LazyPandas_hot. >1 means lazy pandas is faster.
- **Correctness:** all supported queries validated against Polars (group-by
  values within 1e-3; join row counts identical).

## Findings (honest)

We are **behind Polars across most of the H2O suite** at 10M — one win (q2),
competitive on high-cardinality group-by (q3/q5 at 0.72–0.76x), and materially
slower elsewhere. The benchmark surfaced concrete, investigable targets that
the custom microbenchmarks missed:

1. **Low-cardinality group-by is the worst gap — q4 int-key mean is 17x slower
   (0.06x), q1 str-key sum 4x (0.24x).** A 100-group aggregation over 10M rows
   is pure memory-bandwidth work; Polars does it in 13–33 ms, we take
   135–226 ms. This is the most common group-by shape in practice and the
   highest-value thing to fix. Likely cause: not hitting an
   internally-parallel hash aggregation for plain numeric/raw-string keys (the
   dictionary-key fast path that recovered 15x earlier only triggers for
   Categorical columns). **Top follow-up.**

2. **Joins lag, worst on left and large-build.** q3 (left join) 0.08x and q5
   (10M×10M inner) 0.14x. Left joins likely do not take the acero path (acero
   left-join semantics / order), and the 10M-build inner carries string
   payload columns (id4/id5) through the gather — the known Arrow large_string
   `take` wall. q1 (small build) is the best join at 0.61x.

3. **Hot ≥ cold on the largest queries** (q10, join q2/q5): we get no warm-run
   benefit and even regress, where Polars' hot run is faster — suggesting
   per-call allocation/teardown cost (thread pool, Arrow buffers) that Polars
   amortizes. Worth profiling.

4. **Four queries unsupported** — grouped `median` (q6), aggregation arithmetic
   `max-min` (q7), grouped top-k + `explode` (q8), `corr` (q9). These are real
   API/kernel gaps; q6 and q7 are the cheapest to close.

### Priority order for closing the gap

1. Low-cardinality numeric/string group-by (q1, q4) — biggest, most common.
2. Left-join and large-build-join routing (q3, q5).
3. Grouped `median` + aggregation arithmetic (q6, q7) — unlocks 2 queries.
4. Per-call teardown overhead (the hot ≥ cold anomaly).
